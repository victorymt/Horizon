## Publication is anchored to the UTC+8 calendar day

The schedule is `17 16,20,0 * * *`, i.e. 00:17 / 04:17 / 08:17 in UTC+8, and all three attempts resolve to the same UTC+8 report date. The report date comes from `TZ='Asia/Shanghai' date`, so the 16:17 UTC trigger files the *next* date (16:17Z is 00:17 +08 of the following day). Coverage is no longer a rolling lookback: `--hours` was dropped so the window is derived from `HORIZON_REPORT_DATE` as `[previous 00:00 +08, this 00:00 +08)`, enforced as an upper bound so a delayed run cannot leak next-day items into the digest. The backfill guard now accepts the current or next UTC date, because a +08 report date is legitimately one day ahead of UTC late in the day. Runs with no `HORIZON_REPORT_DATE` (local `uv run horizon`) keep the rolling `time_window_hours` lookback with no upper bound.

Two consequences worth knowing. GitHub's scheduler drifts by roughly 4–6.5 hours (observed: 262–394 minutes late on the old `0 0 * * *` cron), so "00:17 (+08)" is intent, not a guarantee — expect publication anywhere from about 04:00 to 07:00 (+08). And because the window is a fixed calendar day, a run that fires late still produces that day's digest rather than skipping a day; the `needed` gate is what prevents a second publish for the same date.
